= fulcro-tui

image:https://img.shields.io/clojars/v/com.fulcrologic/fulcro-tui.svg[link=https://clojars.org/com.fulcrologic/fulcro-tui]
image:https://github.com/fulcrologic/fulcro-tui/actions/workflows/test.yml/badge.svg["CI", link="https://github.com/fulcrologic/fulcro-tui/actions/workflows/test.yml"]

A terminal (TUI) rendering target for https://github.com/fulcrologic/fulcro[Fulcro], backed by https://github.com/jline/jline3[JLine].

Fulcro has always been full-stack CLJC in all ways (rendering and server processing alike). To date the server support for "rendering" has largely been useful for headless testing, but all the machinery for more was always present.

This library (finally) provides an alternative rendering target: The terminal!

it lays out a tree of terminal-native nodes (boxes, text, inputs, buttons) and paints them into a character-cell buffer that is displayed in a real terminal via JLine. Components are written with Fulcro's standard `defsc` macro (their render simply returns a tree of terminal nodes) and driven by the same Fulcro data-management primitives (mutations, normalized state, transactions).

The result is a Fulcro/React-like experience with a terminal UI.

Babashka support made possible by the inclusion of JLine!

[TIP]
====
*New here? Read the link:Guide.adoc[Fulcro TUI Guide].* It is the complete reference —
getting started, the element catalog, layout, focus/keyboard, modals & pickers, the
application lifecycle, performance measurement, and headless testing. This README is just
a quick tour; the link:Guide.adoc[Guide] covers everything in depth.
====

== Status

Clone the report and run the demo under babashka with `bb run tui` — see `bb.edn` for details.

API stable at 1.0.0-RC1. Everything is pretty well-tested on the rendering front, and fast (60fps on my m1 mac).
The Fulcro patterns have been stable for years, but the new bb support of Fulcro is not widely tested, so
expect that if you use something we haven't tried yet, it may not work.

== Try the demo

Run the example two-field form in a real terminal, on the JVM:

[source,bash]
----
clojure -M:tui -m tui-example.form
----

…or under babashka (faster startup, no JVM):

[source,bash]
----
bb run tui
----

Controls:

* *Tab* / *Shift-Tab* move focus through the fields, the multiline notes box, the Save button, and into the item list.
* *Arrow keys* move the caret (in the notes box, Up/Down move by visual line).
* Type to edit the focused field.
* In the multiline notes box, *Enter* inserts a newline (it does not submit); the box wraps to its width and self-scrolls to keep the caret visible.
* *Enter* / *Space* activates the focused Save button or list item.
* *PageUp* / *PageDown* scroll the item list; tabbing into the list auto-scrolls to keep the focused item visible.
* *Pick a fruit* opens a modal list picker (see below): *Up* / *Down* move the highlight, *Enter* chooses, *Escape* cancels.
* *Ctrl-Q* quits.

TIP: To profile the render/I/O pipeline, launch with the `fulcro.tui.perf` system property set
(`bb -Dfulcro.tui.perf=1 tui` or `clojure -J-Dfulcro.tui.perf=1 -M:tui`); the session is profiled
and a self-time report prints after you quit. See the link:Guide.adoc[Guide]'s _Measuring performance_ section.

== A full-stack RAD demo (server + statecharts + Datascript)

`src/demo` is a second, larger example: a https://github.com/fulcrologic/fulcro-rad[Fulcro RAD]
*report → form* combo — an invoice list that opens an editable invoice form with a to-many line-item
subform — driven entirely by https://github.com/fulcrologic/statecharts[statecharts] (routing plus the
RAD report/form engines), talking to a server over a standard Fulcro *transit* `/api`. It exercises a
real cross-section of a Fulcro app against the terminal renderer, and runs the client on the JVM *or*
babashka.

Architecture (two tiers, under `src/demo/tui_demo/`):

* *Server* (JVM): an in-memory https://github.com/tonsky/datascript[Datascript] database behind a
  Pathom 2 parser and a small hand-written RAD Datascript driver, served at `/api` (http-kit + Fulcro's
  transit middleware). `tui_demo.server.*`.
* *Client* (JVM or babashka): the fulcro-tui app + RAD `defsc-report`/`defsc-form` + statechart routing,
  rendered by a small RAD UI plugin that maps reports/forms to terminal elements (installed with
  `install-ui-controls!`, modeled on the semantic-ui plugin). A synchronous transit HTTP remote
  (built on `babashka.http-client`) connects to the server. `tui_demo.{ui,rendering,client}.*`.
* *Model* (CLJC, shared): the RAD attribute model. `tui_demo.model.*`.

Run it — start the server, then the client (in a second terminal):

[source,bash]
----
clojure -M:demo-server      # JVM: Datascript + transit /api on :3001
clojure -M:demo             # JVM client …
bb run demo                 # … or the babashka client (same JVM server)
----

The report lists invoices (customer, date, total); *Tab* / *arrows* move the row highlight, *Enter*
opens the invoice in an edit form (pick-one customer, date, an editable line-item subform with *Add*),
and saving persists back to Datascript through the transit API. *Ctrl-Q* quits.

NOTE: this demo pulls cutting-edge releases of fulcro, statecharts, fulcro-rad and
fulcro-rad-statecharts (see the `:demo` / `:demo-server` aliases in `deps.edn` and the `demo` task in
`bb.edn`). It is an integration showcase, not a packaged template.

== Overlays: modal and picker

A `tui/modal` node is an overlay window that floats over the rest of the UI. The driver composites it
on top of the base tree and *traps focus and keyboard input* to it while it is open, so the controls
behind it are inert. It is declarative — its presence is just app state, via an `:open?` flag:

[source,clojure]
----
(tui/modal {:id :confirm :open? confirm-open?
            :width 30 :height 7 :title "Confirm"
            :on-dismiss #(tui/transact! this [(close-confirm)])} ; Escape calls this
  (tui/text {} "Delete everything?")
  (tui/button {:id :yes :on-activate #(tui/transact! this [(do-delete)])} " Yes "))
----

The library owns no lifecycle: *you* toggle `:open?` (and record any result) with your own mutations,
exactly as the rest of a Fulcro app works. `:width`/`:height` accept a cell count or `[:fraction f]`;
`:align` (default `:center`) positions the window; `:border?` defaults to `true`; `:on-dismiss` is
called on *Escape*.

`tui/picker` is a list picker built on `modal` — a scrollable `:viewport` of selectable rows where the
focused row *is* the highlight (Up/Down move it, the list scrolls to follow, Enter selects, Escape
cancels):

[source,clojure]
----
(tui/picker {:id        :fruit
             :open?     picker-open?
             :title     "Pick a fruit"
             :width     24 :height 8
             :options   [{:value :apple :label "Apple"}
                         {:value :pear  :label "Pear"}]
             :on-select (fn [v] (tui/transact! this [(choose-fruit {:v v})]))
             :on-cancel (fn []  (tui/transact! this [(close-picker)]))})
----

See the demo source in this repository for more examples, and the link:Guide.adoc[Fulcro TUI Guide]
for full coverage of elements, layout, focus/keyboard, overlays, the application lifecycle, and
headless testing.

== Keyboard shortcuts and terminal support

[IMPORTANT]
====
Keyboard shortcuts *require an advanced terminal* that implements the enhanced (Kitty/`CSI u`)
keyboard protocol — for example *iTerm2* (recent versions), *kitty*, *WezTerm*, *Ghostty*, or
*foot*. fulcro-tui detects the protocol at startup. On any terminal that does **not** support it
(including the default macOS *Terminal.app*), the shortcut layer is silently *disabled*: shortcuts do
not fire and no mnemonic hints are shown. Everything else — Tab/Shift-Tab navigation, arrow keys,
typing, and overlays — works on every terminal. Only the shortcut layer is gated.

This requirement exists because plain terminals cannot reliably report modified keys: `Alt`/`Option`
combos are ambiguous (and on macOS `Option` types accented characters unless configured as Meta), and
several `Ctrl` combinations are reserved by the terminal or OS (flow-control `Ctrl-S`/`Ctrl-Q`, signals
`Ctrl-C`/`Ctrl-Z`, and `Ctrl-I`/`Ctrl-M`/`Ctrl-H`/`Ctrl-[` which are byte-identical to Tab/Enter/
Backspace/Escape). The enhanced protocol disambiguates all of these, so we require it rather than ship
shortcuts that work unpredictably.
====

Declare a shortcut directly on a control with `:shortcut` (a chord in `tui/key-chord` form). When the
protocol is active, pressing it focuses the control and — for a button — fires its `:on-activate`
("clicks" it). The chord's base letter is underlined in the label as a hint:

[source,clojure]
----
(tui/button {:id :save :shortcut [:alt "s"]            ; Alt/Option-s; the "S" is underlined
             :on-activate #(tui/transact! this [(save!)])} "Save")

(tui/input {:id :customer :shortcut [:alt "c"] :value name}) ; inputs default to :shortcut-action :focus
----

`:shortcut-action` is `:activate` (default for buttons) or `:focus` (default for inputs, which have no
activation). App-level reserved chords registered in `:global-keymap` (e.g. a quit key) take precedence
over control shortcuts.

=== Focus control

Focus is a single value in app state; move it programmatically with the helpers in
`com.fulcrologic.fulcro.tui.engine`:

* `focus-last-in!` / `focus-first-in!` — focus the last/first focusable inside a container subtree.
  After adding a to-many subform child, call `focus-last-in!` on the *items* container (give the items
  list its own id, excluding the trailing "+ Add" button) to focus the newly-added item.
* `focus-next-in-group!` / `focus-prev-in-group!` — jump between members of a `:focus-group` (e.g. from
  one line-item to the next), skipping the members' inner fields. Tag each member container with the
  same `:focus-group` key and wire the helpers to a chord such as `Ctrl-Down`/`Ctrl-Up`.
